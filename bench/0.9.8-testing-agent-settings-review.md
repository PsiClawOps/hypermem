### Long-horizon query detection

Source: `src/compositor.ts`.

Validate that `isLongHorizonRecallQuery()` is active and recognizes temporal / LoCoMo-style prompts. Signals include:

- temporal: `when`, `before`, `after`, `since`, `first`, `last`, `year`, `month`
- identity / relationship / planning / career / activities questions
- `who`, `where`, `what`, `which`, `how long`, `how many`, `both`, `likely`

This gates the benchmark-specific retrieval posture without changing normal production turns.

### Temporal recall shaping

Source: `src/compositor.ts`, temporal recall path.

Expected 0.9.8 behavior:

- Temporal store query over-fetches `limit: 80`, not the old `15`.
- Query terms are extracted with `recallQueryTerms()`.
- Temporal facts are scored by term overlap.
- Only facts with positive term overlap survive.
- Sorted by recall score, then `occurredAt` descending.
- Injects up to `24` temporal facts.
- Temporal context budget is `30%` of remaining tokens, not the old `20%`.

Intent: avoid answering `when did X` from the latest unrelated temporal row. This is a classic benchmark wrong-date failure.

### Long-horizon semantic recall behavior

Source: `src/compositor.ts`, `buildSemanticRecall(..., longHorizonRecall)`.

Expected 0.9.8 behavior for long-horizon recall only:

- Recency decay is skipped. Old benchmark evidence should not be demoted just because it is old.
- FTS-only result floor is relaxed to `0.015` instead of production `0.05`.
- Episode score floor is not applied for long-horizon recall. Normal production still keeps the episode floor.

Production posture remains stricter. Benchmark posture is deliberately more tolerant of old exact evidence.

### Long-horizon fusion weights

Source: `src/compositor.ts`, `hybridSearch()` call inside `buildSemanticRecall()`.

Expected long-horizon overrides:

```ts
rrfK: 20
ftsWeight: 1.35
knnWeight: 1.0
rerankerMaxDocuments: max(configured, min(hybridLimit, 32))
rerankerTopK: max(configured, min(hybridLimit, 18))
```

Intent: exact names, dates, and objects should separate from semantically-near but wrong old chatter. This is benchmark-specific, not global production fusion.

## Benchmark matrix to run

Run the benchmark as four separate, clean-database trials so each result is attributable. Reset `~/.openclaw/hypermem/bench-locomo` before each trial and preserve the config snapshot, bridge log, doctor output, and score artifact for each run.

1. **EasyLoCoMo against HyperMem 0.9.7**
   - Purpose: pre-0.9.8 baseline.
   - Bridge mode: existing EasyLoCoMo bridge using direct retrieval.
   - Config: current production benchmark settings for the 0.9.7 install.

2. **EasyLoCoMo against HyperMem 0.9.8**
   - Purpose: isolate the 0.9.8 package/code change.
   - Bridge mode: existing EasyLoCoMo bridge using direct retrieval.
   - Config: current production benchmark settings.

3. **EasyLoCoMo against HyperMem 0.9.8 with bounded benchmark profile**
   - Purpose: test whether richer isolated benchmark settings improve recall without changing bridge behavior.
   - Bridge mode: existing EasyLoCoMo bridge using direct retrieval.
   - Config: bounded benchmark profile below.

4. **EasyLoCoMo against HyperMem 0.9.8 with bounded benchmark profile plus `HyperMem.compose()` bridge mode**
   - Purpose: test actual OpenClaw memory composition behavior, including session warming, warm history budget, fact/keystone/cross-session allocation, topic triggers, pressure-aware trimming, and final context packing.
   - Bridge mode: new explicit compose mode, for example `--bridge-mode compose`, not a replacement for the direct retrieval mode.
   - Config: bounded benchmark profile below.
   - Run with memory context as the evidence source, preferably `--no-context`, so answers are not dominated by the raw LoCoMo conversation prompt.

Benchmark 4 should be added as a separate mode rather than replacing the current bridge path. The direct retrieval bridge remains useful because it isolates indexing, FTS/KNN retrieval, and reranker quality. The compose bridge is useful because it measures the path OpenClaw agents actually use.

## Recommendation for the testing agent

### Default recommendation: do not change global warming yet

Position: keep the production fleet warming values as-is for now.

Reason: 0.9.8 specifically widened recall and exact-evidence fusion. If benchmark accuracy is still weak, first validate those paths before raising `warmHistoryBudgetFraction`. Raising warming first is the old trap: it makes turn 1 feel richer, then creates warm-trim-compact cycling. Future outage, but with better vibes.

### Use a separate benchmark profile if the testing agent is isolated

If the testing agent is only for benchmark runs and has low tool-output risk, I recommend testing this bounded profile:

```json
{
  "compositor": {
    "budgetFraction": 0.60,
    "contextWindowReserve": 0.25,
    "targetBudgetFraction": 0.55,
    "warmHistoryBudgetFraction": 0.34,
    "maxFacts": 35,
    "maxHistoryMessages": 700,
    "maxCrossSessionContext": 6000,
    "keystoneHistoryFraction": 0.18,
    "keystoneMaxMessages": 18,
    "wikiTokenCap": 800,
    "maxTotalTriggerTokens": 12000,
    "maxRecentToolPairs": 3,
    "maxProseToolPairs": 10,
    "hyperformProfile": "full"
  },
  "reranker": {
    "minCandidates": 8,
    "maxDocuments": 32,
    "topK": 18,
    "timeoutMs": 2000
  }
}
```

Why these values:

- `warmHistoryBudgetFraction: 0.34` matches the protected warmup floor and gives more cold-start recall without jumping back to the heavy `0.45` posture.
- `budgetFraction: 0.60` gives the benchmark more room without turning the 128k model into a saturation test.
- `targetBudgetFraction: 0.55` gives a bit more room to facts/wiki/keystones while preserving enough message history.
- `maxFacts: 35`, `keystoneMaxMessages: 18`, and `maxCrossSessionContext: 6000` are gentler recall enrichments than raising warming to 0.45+.
- `reranker.topK: 18` and `maxDocuments: 32` align config with the new 0.9.8 long-horizon upper bounds.

Do not use this profile for general long-running tool-heavy agents without pressure telemetry. Benchmark profiles are allowed to be richer because their blast radius is small.

### Tuning order if benchmark score is still weak

1. Validate 0.9.8 recall code paths first: recall breadth, long-horizon detector, temporal shaping, long-horizon fusion.
2. Validate reranker is actually active and not timing out. If timeout rate is high, increasing warming will not fix ranking.
3. Increase `reranker.topK` to `18` and `maxDocuments` to `32` for the testing agent.
4. Increase `maxFacts` to `35`, `keystoneMaxMessages` to `18`, and `maxCrossSessionContext` to `6000`.
5. Only then raise `warmHistoryBudgetFraction`, and cap first trial at `0.34`.
6. If pressure p95 stays below `45%` and turn-1 recall is still cold, test `warmHistoryBudgetFraction: 0.40`.
7. Do not jump to `0.45` unless telemetry shows headroom. That was the older rich posture and is known to create cycling on long-running fleets.

## One config mismatch to review

Current observed config has:

```json
"deferToolPruning": true
```

Global OpenClaw context pruning currently appears to be off:

```json
agents.defaults.contextPruning.mode = "off"
```

For pure benchmark runs this probably does not matter because tool output is small. For real tool-heavy agents, this is worth reviewing: either enable native context pruning intentionally or set `deferToolPruning: false` so HyperMem owns tool-result gradient pruning. Leaving both effectively off is how large tool outputs become a pressure landmine.

## Bottom line

Recommended action for the testing agent:

- Validate 0.9.8 code constants and long-horizon paths first.
- Keep production warming unchanged.
- For the isolated benchmark agent, apply the bounded benchmark profile above.
- Prefer reranker/candidate/fact/keystone enrichment before raising warm-history budget.
